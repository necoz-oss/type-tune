# Compiler validation and build-info artifacts

`apply`, `extract`, and their dry runs validate rewritten TypeScript with the project-local `tsc` where available, falling back to `PATH`. If Vue scripts change, they also run `vue-tsc` after `tsc`. Both receive `--noEmit --project` and a separate, newly created private `--tsBuildInfoFile` path. Compiler `TMPDIR`, `TMP`, and `TEMP` point to that private directory for the invocation. The temporary directories are removed after each compiler exits, including after validation failures; cleanup errors are reported and cause the rewrite to fail or roll back. Existing project build-info files are neither read nor updated by this validation. Successful apply keeps the approved source changes, not validation build-info files; users can run their normal typecheck or build to refresh their caches. Dry-run rolls back the planned changes and removes the temporary build-info files. Failed apply rolls back the planned changes as before.

This prevents the confirmed TypeScript and vue-tsc `.tsbuildinfo` leak, including a configured absolute, relative, inherited or symlinked build-info destination: the command-line override redirects it. Fresh state avoids trusting a stale cache, at the cost of potentially slower validation. The pinned TypeScript 6.0.3 and vue-tsc 3.3.14 were tested with composite and incremental configurations. Other compiler versions must accept `--tsBuildInfoFile`; if a compiler rejects it, validation fails and the transaction rolls back rather than skipping checks. Overriding the output location may affect diagnostics specifically about the original build-info option or location; it does not validate that destination's writability. It is not a general filesystem sandbox: compiler executables, Vue plugins, explicitly configured caches, and other compiler options may have other side effects. Forced termination and concurrent filesystem changes can prevent cleanup. Filesystem snapshots used by the regression tests cover contents, paths, directory presence and symlink targets, but not timestamps, ACLs or other platform metadata. Cross-platform behavior beyond the Linux CI tests has not been established.

## Reproduction and regression

The prior implementation could leak build info even with `--noEmit`. For example, in a disposable project with `{"compilerOptions":{"composite":true,"outDir":"dist"},"include":["src"]}`, an exported interface and two TypeScript referrers, generate and review a plan and run:

```sh
type-tune plan --project tsconfig.json --out plan.json --markdown plan.md
# Approve the candidate in plan.md.
type-tune apply --plan plan.json --markdown plan.md --dry-run
```

On the pre-fix `09e4389a42cc51e460bb283d77edb1415ba9917f` binary this exited 0 and left `dist/tsconfig.tsbuildinfo`; the same reviewed dry-run with the fix exits 0 without that project change. In a separate incremental fixture with a TypeScript error, direct `tsc --noEmit --project tsconfig.json` exited 2 with TS2322 and still created its configured `cache/result.tsbuildinfo`. `pnpm test:vue-tsc` runs the real pinned compiler integration tests, including snapshots for new and existing build info, explicit and inherited destinations, failure rollback, Vue validation and repeated previews. Project `node_modules` is a fixture dependency symlink and is excluded from snapshot traversal; other symlink targets are recorded.

Disabling incremental mode is not an equivalent fix: the pinned compilers reject `--incremental false` with `composite` (TS6379). Tracking presumed artifact paths risks missing inherited or external destinations and deleting user-owned files; validation in a full copied project or OS sandbox would be a larger separate design with different path and dependency semantics. Redirection addresses the confirmed build-info output without claiming arbitrary compiler isolation. The project-reference design investigated in commit `0f8b1da` remains future work; this change does not implement graph traversal or graph-wide validation.
